# contest-prep

[![CI](https://github.com/NKorshunov19/contest-prep/actions/workflows/ci.yml/badge.svg)](https://github.com/NKorshunov19/contest-prep/actions/workflows/ci.yml)

Заготовки, которые я собрал, готовясь к контесту по Java: быстрое чтение ввода, бинарный
поиск по ответу, система непересекающихся множеств, обходы графа, разбор арифметических
выражений и выдача наименьшего свободного номера.

На контесте несколько часов и одна попытка, и время там уходит не на идею, а на мелочи:
в какую сторону округлять середину отрезка, не переполнится ли сумма границ, не упадёт ли
рекурсивный обход на цепочке. Поэтому каждую заготовку я написал заранее по одному разу
и покрыл тестами на те случаи, на которых решение обычно и разваливается: переполнение,
цепочка на миллион элементов, пустой и некорректный ввод.

Стек: Java 21, Maven, JUnit 5, AssertJ, GitHub Actions. Ни Spring, ни базы, ни сети,
из зависимостей только тестовые.

## Запуск

```bash
mvn test    # 94 теста, кроме JDK ничего не нужно
```

`solutions/Main.java` это шаблон, который целиком копируется в окно ответа. Он лежит вне
`src`, Maven его не собирает, и он не импортирует ничего из `contest.*`: на контесте
сдаётся один файл и разрешена только стандартная библиотека. Проверить, что он
компилируется и считает то, что нужно:

```bash
javac solutions/Main.java
java -cp solutions Main < input.txt
```

Классы из `src` в ответ не уходят, нужный кусок переносится в шаблон руками. Библиотека
нужна, чтобы код был написан и проверен заранее, а не чтобы подключаться к нему во время
контеста.

## Что внутри

| Класс | Зачем | Где пригодится |
|---|---|---|
| `io/FastScanner` | чтение чисел байтами, блоками по 64 КБ | вход от 10⁵ чисел, где `Scanner` съедает лимит времени |
| `algo/BinarySearch` | бинарный поиск по ответу для int, long и double | «минимальное X, при котором успеем или хватит» |
| `algo/DisjointSetUnion` | связность при добавлении рёбер | «когда граф станет одним куском», Краскал |
| `algo/Graphs` | BFS и DFS без рекурсии | кратчайшие пути в рёбрах, компоненты связности |
| `algo/ExpressionEvaluator` | разбор `+ - * ( )` рекурсивным спуском | калькуляторы и любой разбор строки по грамматике, типовая задача их контестов |
| `algo/MinFreeNumber` | наименьший свободный номер с возвратом | «полки», «столики», пул идентификаторов |

## Правила контеста, на которых сыпятся

- Класс называется `Main`, всё в одном файле вместе с импортами.
- Ввод только из stdin, вывод только в stdout. Никаких «Введите N:», приглашение
  попадёт в ответ и завалит тест.
- Только стандартная библиотека.
- Баллы частичные, 0–100 за задачу по пройденным тестам, так что недоделанную задачу
  всё равно имеет смысл сдать.
- Во время контеста виден вердикт только по первому тесту, остальные прогоняют после.
  «ОК» не равно 100 баллов, поэтому краевые случаи надо проверять локально самому.
- `out.flush()` в конце обязателен, иначе буфер `PrintWriter` не дойдёт до проверяющего.

## На чём ловят

### Ввод и вывод

`Scanner` разбирает поток регулярными выражениями, и на 10⁵–10⁶ числах это уверенно
съедает секунду-две из лимита. `FastScanner` читает байты блоками по 64 КБ и собирает
число вручную: пропустил всё, что не больше пробела, поймал минус, дальше умножение
на десять. Число копится отрицательным, потому что у `Long.MIN_VALUE` модуль на единицу
больше, чем у `MAX_VALUE`, и через положительное накопление его не прочитать.

Первая версия после конца потока отдавала мусор. `read()` записывал `bytesRead = -1`
и `bufferPointer = 0`, дальше условие «буфер исчерпан» не выполнялось, и метод возвращал
байты из старого буфера. Теперь конец потока это флаг в объекте, а не значение одного
вызова. Заодно `nextLong()` на пустом вводе и на строке `abc` перестал возвращать `0`:
контракт взят у `java.util.Scanner`, `NoSuchElementException` когда данных нет и
`InputMismatchException` когда прочитанное не число или не влезает в тип. Ноль вместо
ошибки это WA, который ищешь час.

Разделитель после числа не съедается, поэтому `nextLine()` предсказуемо отдаёт остаток
текущей строки, а сразу после числа в конце строки возвращает пустую строку.

Вывод ломает людей чаще ввода. Печать в `System.out` в цикле на 10⁵ строк это тот же
лимит времени, поэтому в шаблоне стоит `PrintWriter` поверх `BufferedOutputStream`
и `flush()` в конце.

### Середина отрезка в бинарном поиске

`mid = (lo + hi) / 2` переполняется, когда границы близки к `Integer.MAX_VALUE`, и
поиск уезжает в отрицательные индексы. В целочисленных версиях сумма считается в `long`
и делится сдвигом, на это есть тест по всему диапазону int. Для `long` расширять тип
некуда, там `lo + ((hi - lo) >>> 1)`: разность может уйти в минус, но как беззнаковое
число она верная, и логический сдвиг делит её пополам. С обычным `(hi - lo) / 2` тест
на диапазоне от `Long.MIN_VALUE` до `Long.MAX_VALUE` висел.

В `lastTrue`, который ищет границу истина→ложь, середина округляется вверх. С округлением
вниз на `lo = hi - 1` середина совпадает с `lo`, предикат истинен, `lo` не двигается,
и цикл висит вечно.

Вещественный `firstTrueDouble` идёт фиксированные 100 итераций, а не «пока
`hi - lo > eps`»: на больших числах соседние `double` отстоят дальше заказанной точности,
и условие по eps не выполнится никогда.

Вариант для `long` называется `firstTrueLong`, а не так же, как целочисленный. Сначала
имена совпадали, и вызов вроде `firstTrue(0, 100, x -> ...)` перестал компилироваться:
int-литералы расширяются до `long`, лямбда подходит под обе перегрузки, и компилятор
не может выбрать.

### Стек

`find` в DSU написан итеративно, двумя проходами: первый доходит до корня, второй
перевешивает на него все узлы пути. Рекурсивная версия короче, но до первого сжатия
дерево вполне может быть цепочкой, и на сотнях тысяч элементов это `StackOverflowError`.
На контесте стек не увеличить, `-Xss` в окно ответа не передашь. Тест строит цепочку
из миллиона `union(i, i + 1)` и проверяет `find` под таймаутом.

По той же причине оба обхода графа в `Graphs` идут на `ArrayDeque`, а не на рекурсии,
тест на цепочку из миллиона вершин там тоже есть. Граф хранится списками смежности:
матрица на 10⁵ вершин это 10¹⁰ ячеек.

Отдельно про DSU: она умеет только объединять. Если в задаче рёбра удаляются, процесс
надо разворачивать во времени и добавлять их с конца.

### Разбор выражений

Рекурсивный спуск: три метода, выражение, слагаемое и множитель, и приоритет операций
получается сам собой из того, кто кого вызывает. Слагаемое состоит из множителей, поэтому
умножение сильнее сложения, и таблица приоритетов не нужна.

Переполнение считается через `Math.addExact` и `multiplyExact`: обычные `+` и `*` тихо
заворачиваются по кругу и выдают правдоподобный неправильный ответ, а эти бросают
исключение. Любой некорректный вход превращается в `Optional.empty()`, включая случай
`2+3)`, где префикс разобрался, а хвост остался. Проверка идёт по тому, дошла ли
позиция до конца строки.

Глубина рекурсии здесь равна вложенности скобок, и строка из ста тысяч открывающих
скобок роняла разбор с `StackOverflowError` мимо `catch`, потому что это `Error`,
а не `Exception`. Сейчас стоит предел в тысячу уровней, глубже разбор честно
отказывается. Переписывать спуск на явный стек ради задач, где вложенность маленькая,
я не стал.

### Наименьший свободный номер

Наивное «пробегу и найду первый свободный» это O(n) на запрос. Вместо этого счётчик
никогда не выдававшихся номеров плюс упорядоченное множество освобождённых: если там
что-то есть, берём минимум, иначе выдаём следующий новый. O(log n) на операцию.

Сначала освобождённые лежали в `PriorityQueue`, и она пропускала повторный `release`
одного номера: он попадал в кучу дважды и уходил двум владельцам. `TreeSet` такое
замечает, повторное освобождение теперь бросает исключение, как и освобождение номера,
который не выдавался.

## Тесты

| Класс | Что проверяет |
|---|---|
| FastScannerTest | числа через пробелы и переводы строк, границы long и int, конец ввода, не число, токен длиннее буфера, `nextLine` после числа, `\r\n`, миллион чисел по времени |
| BinarySearchTest | обе границы, «истины нет нигде», весь диапазон int и long, отрезок из одной точки, перевёрнутый диапазон, вещественный поиск |
| DisjointSetUnionTest | транзитивность, повторное объединение, цепочка на миллион элементов, элемент вне диапазона, пустая и отрицательная размерность |
| GraphsTest | расстояния BFS, кратчайший путь вместо первого найденного, компоненты, граф без вершин, петли и кратные рёбра, 1-индексация, цепочка на миллион вершин |
| ExpressionEvaluatorTest | приоритет и скобки, левая ассоциативность, пробелы и табуляции, 11 некорректных строк, переполнение long, `Long.MIN_VALUE` через унарный минус, предел вложенности |
| MinFreeNumberTest | номера подряд, освобождённый выдаётся раньше нового, повторное освобождение и чужой номер отвергаются, миллион операций по времени |

## Что не сделано

- Нет сегментного дерева, Дейкстры и своих сортировок. Брал то, что чаще нужно в первых
  задачах контеста, остальное не успел.
- Шаблон один и заточен под «число, потом строка чисел». Задачу с несколькими тестами
  в одном запуске придётся править на месте.
- Бенчмарков нет. Что `FastScanner` быстрее `Scanner`, я знаю из устройства обоих,
  а не из замера в этом репозитории.
- В вычислителе нет деления, а вложенность скобок ограничена тысячей уровней.
- `firstTrue` при «истины нет нигде» возвращает `hi + 1`, и на `hi == Integer.MAX_VALUE`
  это переполнится. Чинить без смены сигнатуры нельзя, а на контесте верхняя граница
  всегда с запасом.
